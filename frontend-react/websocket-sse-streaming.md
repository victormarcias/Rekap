# WebSocket / SSE / Streaming

Three ways to send data from server to client beyond HTTP's classic request/response, each solving a different problem.

## WebSocket — bidirectional

A persistent, full-duplex connection: once open, both client and server can send messages at any time, without one having to "ask" the other. Starts as a normal HTTP request that does a protocol *upgrade*.

```js
const socket = new WebSocket('wss://api.myapp.com/chat');
socket.onmessage = (event) => console.log('Received:', event.data);
socket.send('hello');  // the client can also initiate sending at any moment
```

**When to use it**: chat, real-time collaborative editing, any case where the client also needs to push data over the same channel (not just receive).

## SSE (Server-Sent Events) — unidirectional

The server sends events to the client over a normal HTTP connection (no protocol upgrade) — the client **can't** send data over that same channel, only receive. Simpler than WebSocket when the reverse direction isn't needed, and the browser reconnects automatically if it drops.

```js
const events = new EventSource('/api/notifications');
events.onmessage = (event) => console.log('Notification:', event.data);
// there's no events.send() — SSE is strictly server → client
```

**When to use it**: live notifications, feeds, progress of a long-running task — any case where the data flow is only server → client.

## Streaming (fetch + `ReadableStream`)

A normal HTTP response, but sent in pieces (*chunked*) as the server generates them, instead of waiting to have the complete response. Not a separate protocol like WebSocket/SSE — it's the same regular request, read incrementally.

```js
const response = await fetch('/api/generate');
const reader = response.body.getReader();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  console.log(new TextDecoder().decode(value)); // each chunk as soon as it arrives, not at the end
}
```

**When to use it**: the typical case today is text generated by an LLM token by token — the user sees the response appear progressively instead of waiting for the whole output to finish.

## Comparison

| | WebSocket | SSE | Streaming |
|---|---|---|---|
| Direction | Bidirectional | Server → client | Server → client |
| Protocol | Upgrade to `ws://` | Normal HTTP | Normal HTTP |
| Automatic reconnection | No (has to be implemented) | Yes, native to the browser | Not applicable (one request, one stream) |
| Typical case | Chat, live collaboration | Notifications, feeds | Long, incrementally generated responses |
